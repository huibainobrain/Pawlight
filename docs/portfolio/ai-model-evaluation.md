# Pawlight：AI 模型评测与选型

> 我在 Pawlight 中真正要解决的不是“接哪个模型 API”，而是：**这个场景最不能接受模型犯什么错，以及如何围绕这个错误完成模型选择、产品兜底和上线后的持续评测。**

## 1. 场景里的核心错误是什么

Pawlight 的 AI 能力会根据已经离世宠物的真实照片生成新的纪念场景。

因此用户首先判断的不是：

> 画面漂亮吗？

而是：

> **这还是我的那只宠物吗？**

所以模型优先级不是常规的：

```text
美观 → 创意 → 清晰度
```

而是：

```text
身份保持
> 场景遵循
> 风格稳定
> 动态自然
> 延迟 / 成本 / 稳定性
```

其中身份保持是硬门槛。

需要重点保持：

- 毛色；
- 复杂斑纹；
- 脸型；
- 耳形；
- 眼睛；
- 体型；
- 长短毛；
- 明显个体特征。

如果身份已经漂移，背景再漂亮也应判为失败。

---

## 2. 为什么没有直接训练单宠 LoRA

早期考虑过：

### 路线 A：参考图生成

```text
Pet Photo + Prompt
→ 通用模型
```

优点：

- 用户只需一张已有照片；
- 无需训练；
- 首次体验快；
- 成本低；
- API 容易替换。

问题：

- 个别复杂宠物会身份漂移。

### 路线 B：单宠 LoRA / DreamBooth

理论上可以进一步加强一致性，但会增加：

- 多照片采集；
- 单宠训练；
- 训练等待；
- 单宠模型资产；
- 失败重训；
- 更高首次使用门槛。

对于当前 MVP，这些成本发生得太早。

因此当前选择：

> **参考图生成 + 多候选 + 主人选择。**

先用产品机制解决模型不确定性，再判断是否值得进一步增加训练成本。

---

## 3. 评测集怎么设计

只测几只“白色、正脸、高清”的宠物，会明显高估模型能力。

评测样本至少覆盖：

```text
猫 / 狗
浅色 / 深色
纯色 / 复杂花纹
长毛 / 短毛
正脸 / 侧脸
高清 / 老照片
简单背景 / 复杂背景
普通外观 / 强个体特征
```

每只宠物使用同一组场景 Prompt 跑不同模型，减少 Prompt 差异对结果的干扰。

---

## 4. 模型评测维度

| 维度评测重点 |                            |
| ------ | -------------------------- |
| 身份保持   | 是否仍像同一只宠物                  |
| 场景遵循   | 是否正确理解地点、姿态与氛围             |
| 风格稳定   | 多 Case 是否保持统一视觉方向          |
| 局部正确性  | 眼睛、耳朵、四肢、尾巴是否异常            |
| 跨场景一致性 | 同一宠物换场景后是否仍保持身份            |
| 可控性    | Prompt / Reference 是否真正起作用 |
| 延迟     | 平均与 P95                    |
| 成功率    | API / 内容生成成功率              |
| 成本     | 一次最终成功体验的真实生成成本            |

其中：

```text
身份保持不通过
→ 直接失败
```

而不是依靠综合平均分抵消。

## 6. 为什么最终不是“让模型自动选最好的一张”

即使未来增加自动相似度评分，我仍然不会直接让系统决定：

> 哪张最像 TA。

最终产品流程：

```text
生成 4 张
→ 主人选择
→ 视频生成
```

这是 Human-in-the-loop。

原因：

### 模型解决生成问题

模型负责扩大候选空间。

### 主人解决身份判断问题

“像不像”包含大量长期私人记忆。

### 产品吸收模型随机性

模型不需要做到“一次必对”，才能形成可用体验。

同时，用户选择本身也可以成为未来评测信号。

---

## 7. 视频评测关注什么

观察窗并不是短视频产品。

它不需要复杂镜头，而需要：

> **这张纪念画面仿佛在轻轻继续。**

重点检查：

- 宠物不能持续变脸；
- 毛色 / 花纹不能漂移；
- 呼吸、眨眼等微动自然；
- Camera 尽量稳定；
- 不频繁切镜；
- 首尾变化较小，适合循环。

所以目标不是生成更长的视频，而是生成更适合长期反复观看的动态。

---

## 8. 模型问题不能只靠 Prompt 解决

Pawlight 对生成质量的控制分四层：

```text
模型层
选择更合适的基础能力

Prompt 层
身份保持 + 场景 + 风格 + 负向约束

产品层
4 候选 + 主人选择 + 重生成限制

系统层
失败态 + Job + R2 + 原照片 fallback
```

这是我认为 AI 产品设计里很重要的一点：

> **不能要求模型独自承担整个产品正确性。**

---

## 9. Provider：为什么模型选型必须可持续变化

当前抽象：

```text
ImageGenProvider
VideoGenProvider
```

当前：

```text
Ark
→ 已实现 + Live API 验证

Fake
→ 开发 / 测试

其他 Provider
→ 完成 Adapter + 验证后才能接入
```

新增模型需要经过：

```text
Adapter
→ Contract Test
→ E2E Regression
→ Live Smoke
→ 真实 Case 人评
→ 成本 / 时延 / 成功率检查
→ Production
```

因此模型选型不是一次性的“宣布赢家”，而是一套能够继续重新选择的机制。

---

## 10. 上线后应该怎么继续评

比离线 Benchmark 更重要的最终指标是：

```text
首轮候选接受率
重生成率
最终生成成功率
平均耗时 / P95
单次成功生成成本
恢复原照片比例
“不像 TA”Bad Case 占比
不同宠物类型失败分布
```

最终形成：

```text
真实用户 Case
→ 行为 / Bad Case
→ 归因
→ 模型 / Prompt / 参数 / 交互调整
→ 回归
```

---

## 最终方法

Pawlight 让我形成的模型选型方法不是：

> 谁 Benchmark 第一，就接谁。

而是：

> **先找到这个用户场景里最昂贵的模型错误，再围绕它设计评测、交互和工程体系。**

Pawlight 中最昂贵的错误就是：

**主人认不出自己的宠物。**
